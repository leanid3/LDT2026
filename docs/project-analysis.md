# Разбор проекта «Инспектор ИИ» и карта интерфейса

## Коротко: что это за проект

По двум переданным файлам проект называется «Инспектор ИИ API». Это веб-интерфейс для инспектора строительного надзора: пользователь загружает комплект проектной, рабочей и исполнительной документации, система извлекает параметры и сравнивает их, а инспектор разбирает расхождения по доказательствам и принимает решение. После проверки протокол можно финализировать; предусмотрена передача результата в ИАИС «РиН».

Это не система проведения учебного демонстрационного экзамена СПО. В материалах нет заданий для студентов, площадок, критериев экзамена или оценивания компетенций. Вероятнее всего, под «демоэкзаменом» здесь имеется в виду демонстрация/демо проекта. Внешний смысл слова «демонстрационный экзамен» в СПО — практическая оценка профессиональных навыков выпускника, но такой сценарий к данному API не относится ([Минпросвещения: о демонстрационном экзамене](https://edu.gov.ru/press/10115/bolee-392-tysyach-vypusknikov-kolledzhey-i-tehnikumov-sdali-demoekzamen-v-iyune)).

ИАИС «РиН» расшифровывается как информационная система «Разрешения и нарушения»; в контексте строительного надзора она связана с учетом объектов и надзорными процессами ([описание системы в материалах о строительном надзоре Москвы](https://www.mos.ru/upload/content/files/ITOGFORMADOKLADA%2803032022%29.pdf)). Сам API обещает синхронизацию с ней, но подробного контракта передачи данных в приложенных материалах нет.

## Какую задачу решает пользователь

1. Находит строительный объект или создает его.
2. Создает проверку и загружает файлы.
3. Загружает реестр, чтобы связать файлы со стадией документации, шифром и редакцией.
4. Запускает обработку и ждёт, пока документы будут разобраны.
5. Просматривает протокол: подтверждает нарушение, отклоняет ложное расхождение или запрашивает уточнение.
6. Открывает первичные документы рядом, сверяет цитату и подсветку места на странице.
7. Завершает проверку и следит за передачей статуса в ИАИС «РиН».

ПД — проектная документация, РД — рабочая документация, ИД — исполнительная документация. Реестр критически важен: по frontend-api.md без него у файлов не назначается стадия и проверка не сможет корректно сопоставить документы.

## Предлагаемая структура страниц

### 1. Вход

**Зачем:** закрытый рабочий инструмент, API требует Bearer-токен.

**Что видит пользователь:** логин и пароль, ошибки входа, состояние загрузки. После входа приложение получает профиль и роль (`inspector`, `supervisor`, `admin`, `ml_engineer`). Роль влияет на доступные действия.

**API:** `POST /auth/login`, затем `GET /auth/me`.

**Почему это отдельная страница:** нельзя показывать рабочие данные до определения пользователя и его полномочий.

### 2. Список объектов

**Зачем:** стартовая точка ежедневной работы — найти объект, по которому будет проверка.

**Что показывать:** название, адрес, заказчик/подрядчик, номер разрешения (если есть), число/дата последних проверок и статус последней проверки. Поиск и пагинация контрактом пока не предусмотрены, поэтому для первой версии достаточно списка и простых фильтров только если серверная выборка это позволяет.

**Действия:** открыть объект; создать объект.

**API:** `GET /objects`, `POST /objects`.

### 3. Карточка объекта и история проверок

**Зачем:** показать контекст объекта и все проверки, не смешивая разные комплекты документов.

**Что показывать:** реквизиты объекта, список процессов от новых к старым, статус, сценарий (какие стадии документации доступны), время создания/обновления и финализации.

**Действия:** открыть проверку; начать новую загрузку.

**API:** `GET /objects/{id}`, `GET /objects/{id}/processes`.

### 4. Создание проверки и загрузка документов

Лучше оформить это как одну страницу-мастер с четырьмя шагами, а не как четыре несвязанных пункта меню.

**Шаг 4.1 — выбрать объект и файлы.** Проверка привязывается к объекту. Ограничения из frontend-api.md: PDF/DOCX/XML, до 50 МБ на файл и 200 МБ на пакет. API сначала регистрирует метаданные и выдает временные адреса загрузки.

**Шаг 4.2 — передать файлы в хранилище.** Браузер отправляет файлы напрямую в MinIO по выданным URL. Пользователю нужен наглядный прогресс по каждому файлу и возможность повторить неудачную отправку.

**Шаг 4.3 — подтвердить и проверить файлы.** Показать, какие документы приняты, а какие отклонены (неподдерживаемый формат, превышен размер, поврежден файл, вирус). Дальше идут только принятые файлы.

**Шаг 4.4 — загрузить реестр.** Пользователь прикладывает CSV/JSON/XLSX, связывающий документы со стадией ПД/РД/ИД, дисциплиной, шифром, редакцией и статусом согласования. Показать число сопоставленных и несопоставленных строк, ошибки, а также список файлов и распознанные редакции.

**API:** `POST /documents/upload`, загрузка по `upload_url`, `POST /documents/{process_id}/confirm`, `POST /documents/{process_id}/registry`, `GET /processes/{id}/files`.

**Почему мастер необходим:** тут есть несколько разных серверных шагов и два места, где пользователь должен увидеть ошибки до запуска дорогостоящей обработки. API описывает дозагрузку в существующий процесс, но только пока статус процесса это допускает.

### 5. Подготовка и ход обработки

**Зачем:** после загрузки система асинхронно разбирает документы; пользователь не должен гадать, завершилась ли работа.

**Что показывать:** текущий статус (`PENDING`, `PARSING`, `READY` и далее), доступность ПД/РД/ИД, сценарий сравнения, список файлов и время последнего обновления. Пока задача выполняется, обновлять статус опросом примерно раз в 2 секунды, как предлагает frontend-api.md.

**Действие:** кнопка «Запустить проверку» до старта. Если все готово, переход к протоколу.

**API:** `GET /processes/{id}`, `GET /processes/{id}/files`, `POST /processes/{id}/start`.

### 6. Протокол проверки — основной рабочий экран инспектора

**Зачем:** это место, где инспектор принимает решения по результатам ИИ.

**Что показывать:** счетчики по статусам, фильтры по приоритету и результату, список карточек. Карточка должна содержать код и название параметра, ожидаемое и фактическое значения, единицу, разницу, приоритет и простое объяснение системы. В первую очередь выводить `CANDIDATE`, то есть элементы, которым нужно решение человека.

Другие состояния: совпадение (`NEGATIVE_VERIFIED`), недостаточно доказательств (`MISSING_EVIDENCE`), нельзя сравнить (`NOT_COMPARABLE`), не применимо (`NOT_APPLICABLE`), требуется уточнение (`CLARIFICATION_REQUIRED`), подозрение (`SUSPICION`). Подтвержденное нарушение — результат решения человека, а не автоматический вердикт системы.

**Действия по карточке:** подтвердить нарушение; отклонить расхождение с обязательной причиной и комментарием; запросить уточнение. Решение должно фиксироваться вместе с автором и временем.

**API:** `GET /processes/{id}/protocol`, `GET /findings/{id}`, `POST /findings/{id}/decision`, `GET /params` для подписей параметров.

### 7. Просмотр доказательств рядом с карточкой

**Зачем:** инспектору нужно проверить первоисточник, а не принимать результат модели на веру.

**Что показывать:** рядом две стороны сравнения (обычно ПД и РД/ИД), страницу, дословную цитату, извлеченное значение и подсветку фрагмента. На узком экране просмотрщик можно открывать в панели поверх списка.

**API:** данные `evidence[]` приходят в finding; `GET /files/{file_id}/download-url` выдает короткоживущую ссылку на документ. `bbox` задает прямоугольник подсветки в координатах от 0 до 1; если координат нет, показывать страницу и цитату без точной подсветки.

**Почему это часть протокола:** просмотр документа нужен при принятии решения, это не самостоятельная бизнес-задача. Отдельная полноэкранная страница полезна только если просмотр PDF требует много места.

### 8. Завершение проверки и синхронизация

**Зачем:** зафиксировать результаты после того, как инспектор разобрал все спорные пункты.

**Что показывать:** итоговые количества, число нерешенных кандидатов, состояние протокола, кнопку финализации и затем состояние синхронизации с ИАИС «РиН». Если система блокирует финализацию, объяснить, какие решения остались.

**API:** `POST /processes/{id}/finalize`, `GET /processes/{id}/sync`. Отмена финализации доступна только `supervisor`/`admin` и требует причины: `POST /processes/{id}/unfinalize`.

**Важно:** финализация запрещает менять проверку и дозагружать документы. Поэтому действие должно сопровождаться понятным итогом и явным подтверждением в интерфейсе.

### 9. Справочник параметров (второй приоритет)

**Зачем:** дать пользователю возможность расшифровать код параметра Матрицы и понять, из каких частей документов берется значение.

**Что показывать:** код, раздел, название, единицу, приоритет, тип данных, источники в ПД/РД/ИД и логику связи. Каталог содержит 132 параметра по описанию API.

**API:** `GET /params`.

**Рекомендация:** для первого демонстрационного сценария достаточно встроить расшифровку в карточку finding; отдельную страницу справочника делать, если ей действительно будут пользоваться.

## Роли и права в интерфейсе

- **Инспектор (`inspector`)**: загрузка/просмотр документов, просмотр протокола, решения по findings, финализация (точный допуск финализации для этой роли нужно подтвердить у владельца процесса; API описывает ограничение для отмены финализации, но не все права подробно).
- **Руководитель (`supervisor`)**: функции инспектора и отмена финализации с причиной.
- **Администратор (`admin`)**: функции руководителя в части отмены финализации.
- **ML-инженер (`ml_engineer`)**: роль перечислена в API, но отдельные экраны или API-функции для нее не описаны.

## Что реально покрыто API и чего не хватает

**Покрыто:** вход и профиль, объекты, история процессов, регистрация и загрузка файлов, проверка файлов, реестр, запуск и статус обработки, просмотр списка файлов, протокол и доказательства, решения инспектора, финализация и статус синхронизации, каталог параметров.

**Не описано/не покрыто:** экспорт протокола в PDF/XML/DOCX; поиск и пагинация; управление пользователями и матрицей; отдельный список подозрений; разбиение finding; push-уведомления; обновление токена. Это прямо отмечено в frontend-api.md. Не следует обещать такие функции в демонстрации как уже реализованные.

**Неясные продуктовые решения, которые следует закрыть до дизайна:**

1. Какие сочетания стадий считаются допустимыми и как интерфейс объясняет частичный комплект (`FULL`, `PD_RD_ONLY`, `PD_ID_ONLY`, `RD_ID_ONLY`, `SINGLE_ONLY`, `PARTIALLY_LOADED`).
2. Кто именно имеет право финализировать и какие права у `ml_engineer`.
3. Что пользователь увидит при провале синхронизации и можно ли повторить ее (в API есть чтение статуса, но нет ручки повтора).
4. Нужен ли экспорт результата и в каком формате.
5. Как устроен реестр на практике: где взять шаблон и какие ошибки можно исправить без повторной загрузки.
6. Есть ли у демо подготовленные данные/учетные записи и стабильный backend. В frontend-api.md указаны тестовые логины, Swagger и локальные URL, но это инструкции автора документа, а не гарантия работающего стенда.

## Рекомендуемый объем первой демонстрационной версии

1. Вход.
2. Список объектов и создание объекта.
3. Карточка объекта с проверками.
4. Мастер загрузки документов и реестра.
5. Экран обработки со статусами.
6. Протокол с фильтрами и просмотрщиком доказательств.
7. Завершение и статус синхронизации.

Справочник параметров лучше сначала показать как контекстные подсказки. Управление пользователями, редактирование Матрицы и экспорт не планировать как готовые страницы, пока для них нет API.

## Сквозной пример для показа

Открыть объект → создать проверку → загрузить ПД и РД → приложить реестр → показать статусы файлов → запустить обработку → открыть одно расхождение с цитатами в обоих документах → подтвердить или отклонить его с объяснением → показать, что после разбора всех кандидатов проверка завершается → финализировать → показать статус передачи в ИАИС «РиН».

Такой сценарий показывает ценность продукта: ИИ находит потенциальное расхождение и поднимает доказательства, а окончательный вывод делает инспектор.

## Материалы-источники и границы разбора

- `frontend-api.md` — навигационное описание сценария фронтенда, загрузки и ограничений.
- `openapi.yaml` — контракт API версии 0.3.0. Он определяет доступные операции и структуры данных, но не содержит готового дизайна страниц и не доказывает, что backend уже развернут.
- Публичные источники использованы только для различения термина «демонстрационный экзамен» СПО и упоминания ИАИС «РиН»; назначение продукта и пользовательский сценарий выведены из приложенных материалов.
