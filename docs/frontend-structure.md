# Структура фронтенда «Инспектор ИИ»

> Проектируем интерфейс с нуля по двум исходным материалам: `frontend-api.md` и `openapi.yaml` версии 0.3.0. Это спецификация страниц и пользовательских сценариев, не описание уже существующего приложения. API определяет доступные данные и действия; внешний вид, навигация и часть состояний — продуктовые предложения.

## 1. Что за продукт

«Инспектор ИИ» помогает проверять строительную документацию по объекту. Пользователь загружает файлы проектной (ПД), рабочей (РД) и исполнительной документации (ИД), прикладывает реестр, запускает автоматическую обработку, затем разбирает найденные расхождения и подтверждает решения. У каждого спорного результата показываются документы, страницы и цитаты, на которых он основан. После ручной проверки процесс финализируется, статус передачи результата отображается отдельно.

Ключевой принцип интерфейса: система находит кандидатов и показывает основания; решение о нарушении принимает инспектор.

## 2. Главная навигационная модель

Это рабочая система вокруг **объектов**, а внутри каждого объекта находятся **проверки**. Поэтому основная навигация должна быть такой:

- **Объекты** — список строительных объектов и создание нового.
- **Проверка** — отдельный процесс для комплекта документов конкретного объекта. Внутри него разделы: «Обзор», «Документы», «Протокол».
- **Параметры Матрицы** — справочник, если его решат сделать доступным самостоятельным разделом. На первую версию можно вынести расшифровку параметров прямо в протокол.

Не делать главным пунктом меню «Файлы»: файлы относятся к объекту и конкретной проверке. Не делать пункт «Пользователи» или «Настройки Матрицы»: для этих функций в переданном API нет операций.

## 3. Общая оболочка приложения после входа

### Верхняя шапка

Слева направо:

1. Логотип/название **Инспектор ИИ** — переход в список объектов.
2. Хлебные крошки, когда открыты объект или проверка: `Объекты / [Название объекта] / Проверка от [дата]`.
3. Индикатор текущего раздела или заголовок страницы.
4. Информация о текущем пользователе: имя и роль. Меню профиля может содержать «Выйти».

API возвращает имя, логин и роль, но не описывает редактирование профиля. Не добавлять настройки аккаунта без отдельного требования.

### Левая навигация

После входа — компактное постоянное меню:

- Объекты
- Параметры Матрицы (можно скрыть в первой версии или оставить ссылкой в меню)

Разделы «Обзор / Документы / Протокол» показывать как локальные вкладки выбранной проверки, а не как глобальное меню.

### Нижняя часть страницы / футер

У внутреннего рабочего интерфейса постоянный большой футер не нужен: он отнимает место у таблиц и документов. Внизу страницы допустима компактная строка:

- название и версия интерфейса, если версия предоставляется командой;
- ссылка/кнопка «Сообщить о проблеме» — полезно приложить `request_id` из ответа ошибки, но отдельного API для отправки сообщения нет; в первой версии это может быть копирование ID и текстовая подсказка;
- технический статус сервиса — только если появится источник статуса. В текущем OpenAPI `/healthz` и `/readyz` не описаны, значит не обещать его как рабочий индикатор без отдельной интеграции.

Футер страницы входа может содержать только название продукта и версию. Контакты поддержки, политику обработки данных и юридические ссылки исходные материалы не задают — не выдумывать их.

### Общие элементы

- Уведомления об успехе и ошибке с человекочитаемым текстом API.
- Ошибка API: показать сообщение, при наличии — код и `request_id`, дать повторить безопасный запрос.
- Состояния загрузки, пустого списка, отсутствия доступа, ошибки сети и истекшей сессии.
- Сессия по токену до 12 часов; refresh API нет. При 401 отправлять пользователя на вход с сообщением о завершении сессии.
- Подтверждение только для необратимо значимого действия финализации; обычные переходы не блокировать лишними диалогами.

## 4. Страницы подробно

## Страница 1. Вход

**Маршрут-пример:** `/login`

**Задача:** авторизовать сотрудника.

**Шапка:** логотип/название продукта; без основной навигации.

**Основная область:**

- заголовок «Вход в систему»;
- поле «Логин»;
- поле «Пароль» с переключателем видимости;
- кнопка «Войти»;
- место для ошибки: неверные учетные данные, нет связи с сервером.

**Футер:** компактная подпись с названием продукта/версией, если версия известна.

**Данные и действия:** `POST /auth/login`, затем `GET /auth/me`. После успешного входа — переход в «Объекты».

**Не добавлять без подтверждения:** регистрацию, восстановление пароля, вход через SSO — API таких операций не содержит.

## Страница 2. Объекты

**Маршрут-пример:** `/objects`

**Задача:** найти объект и начать работу.

**Шапка:** общая шапка приложения; заголовок «Объекты»; основная кнопка «Создать объект».

**Основная область:**

- строка поиска — желательна для удобства, но фильтрации на API нет; если поиск нужен по всем объектам, потребуется поиск на сервере или приемлемый объем списка;
- таблица/список объектов;
- рекомендуемые колонки: название, адрес, заказчик, подрядчик, номер разрешения;
- дополнительная сводка по последней проверке возможна только после загрузки процессов для каждого объекта; API не включает последнюю проверку в объектный список. Не делать такой столбец обязательным до проверки производительности API;
- пустое состояние с призывом создать первый объект.

**Действия:** открыть карточку объекта; создать новый.

**API:** `GET /objects`.

**Важно:** контракт не предоставляет поиск, сортировку и пагинацию. Не показывать фиктивные серверные фильтры. Для небольшого списка можно фильтровать уже полученные записи на клиенте, если API действительно возвращает полный список.

## Страница 3. Создание объекта

**Маршрут-пример:** `/objects/new` или модальное окно поверх списка.

**Задача:** завести карточку объекта, к которой будут привязаны проверки.

**Шапка:** хлебные крошки `Объекты / Новый объект`, кнопка «Назад».

**Основная область — форма:**

- обязательное поле «Название объекта»;
- «Адрес»;
- «Заказчик»;
- «Подрядчик»;
- «Номер разрешения».

Поля кроме названия необязательны по контракту. `external_id` есть в OpenAPI, но назначение в пользовательском сценарии не раскрыто — не показывать обычному пользователю без решения владельца продукта.

**Кнопки:** «Создать объект», «Отмена».

**API:** `POST /objects`.

**После сохранения:** перейти в карточку объекта.

## Страница 4. Карточка объекта

**Маршрут-пример:** `/objects/{objectId}`

**Задача:** дать контекст объекта и открыть нужную проверку.

**Шапка:** хлебные крошки `Объекты / [Название]`; заголовок объекта; основная кнопка «Новая проверка».

**Основная область:**

1. **Реквизиты:** адрес, заказчик, подрядчик, номер разрешения.
2. **История проверок:** дата создания/обновления, статус, сценарий сравнения, дата финализации при наличии.
3. Сортировка — новые проверки сверху, как указано в документации.
4. Пустое состояние: «Проверок еще нет» и кнопка «Создать проверку».

**API:** `GET /objects/{id}`, `GET /objects/{id}/processes`.

**Действия:** открыть проверку; начать новую загрузку.

## Страница 5. Новая проверка: мастер загрузки

**Маршрут-пример:** `/objects/{objectId}/checks/new`

**Задача:** создать процесс проверки и подготовить комплект документов к обработке. Это одна страница-мастер с шагами и сохранением прогресса, а не четыре независимых страницы верхнего меню.

**Шапка:** хлебные крошки; название объекта; индикатор шагов:

`1 Файлы → 2 Загрузка → 3 Проверка файлов → 4 Реестр → Готово`.

### Шаг 1. Выбрать файлы

- зона перетаскивания и кнопка выбора файлов;
- показать имя и размер каждого файла;
- ограничения из frontend-api.md: PDF, DOCX, XML; до 50 МБ на файл и до 200 МБ на пакет;
- API принимает `original_name` и `size_bytes`.

### Шаг 2. Передать файлы

- отдельный прогресс каждой отправки;
- общий прогресс пакета;
- кнопка повтора для неудачного файла;
- не давать перейти дальше, пока отправки не завершились.

Технически API выдает `upload_url` и `upload_fields`, а браузер отправляет multipart напрямую в хранилище. Пользователю показывается обычный прогресс загрузки, детали presigned URL не нужны.

### Шаг 3. Результат проверки файлов

Показать статус каждого файла: принят, загружается, отклонен по формату/размеру/повреждению/вирусу; если есть — текст `check_error`, число страниц. Дать удалить/заменить отклоненный файл — только если API и серверный процесс это поддерживают; в контракте отдельной операции удаления нет, поэтому безопасно обещать только повторную загрузку через новый процесс/сценарий.

### Шаг 4. Реестр документов

- пояснение, зачем он нужен: связывает файл со стадией ПД/РД/ИД, шифром, дисциплиной и редакцией;
- ссылка «Скачать шаблон» возможна лишь после создания шаблона; сейчас шаблонного эндпоинта/файла в переданных материалах нет;
- загрузка CSV, JSON или XLSX;
- результат: всего строк, сопоставлено, не сопоставлено, ошибки;
- после разбора — список документов с найденными стадиями и редакциями, признак актуальности.

**Обязательная подсказка:** без реестра проверка не сможет правильно распределить документы по стадиям и выбрать актуальные версии — это прямо указано в frontend-api.md.

**API по шагам:**

- `POST /documents/upload` — создать процесс или получить слоты для дозагрузки;
- прямой POST в `upload_url` для каждого файла;
- `POST /documents/{process_id}/confirm`;
- `POST /documents/{process_id}/registry`;
- `GET /processes/{id}` и `GET /processes/{id}/files`.

**Завершение мастера:** кнопка «Перейти к проверке»/«Запустить проверку» доступна после успешной загрузки и обработки реестра. Правило допуска запуска в материалах описано неполно: проверить его с владельцем backend; интерфейс должен опираться на фактический ответ API.

## Страница 6. Проверка: обзор и обработка

**Маршрут-пример:** `/checks/{processId}`

**Задача:** показать комплектность, статус процесса и дать контролируемо запустить анализ.

**Шапка:** хлебные крошки; объект и дата проверки; бейдж статуса; вкладки `Обзор`, `Документы`, `Протокол`.

**Основная область:**

- прогресс по стадиям ПД/РД/ИД со статусами загружено/частично/отсутствует;
- сценарий сравнения (например, ПД↔РД или только один комплект);
- количество файлов и их текущие редакции;
- последовательность статусов: `PENDING → PARSING → READY → VERIFYING → COMPLETED → FINALIZED`;
- временная шкала или пошаговый индикатор обработки;
- кнопка «Запустить проверку» только в допустимом статусе;
- при `PARSING` — сообщение, что обработка идет, автоматическое обновление примерно каждые 2 секунды;
- при ошибке/неполном наборе — конкретное объяснение по данным API.

**API:** `GET /processes/{id}`, `GET /processes/{id}/files`, `POST /processes/{id}/start`.

**Состояния:**

- `PENDING`: подготовка завершена, доступен запуск, если backend это разрешает;
- `PARSING`: система разбирает документы;
- `READY`: можно открыть результаты/начать верификацию;
- `VERIFYING`: инспектор принимает решения;
- `COMPLETED`: решения закончены, можно финализировать;
- `FINALIZED`: изменения заблокированы.

Семантику ошибки обработки и возможность повторного запуска OpenAPI подробно не определяет.

## Страница 7. Проверка: документы

**Маршрут-пример:** `/checks/{processId}/documents`

**Задача:** проверить, какие именно файлы вошли в обработку и какие редакции система считает актуальными.

**Шапка:** та же шапка проверки и вкладки; заголовок «Документы».

**Основная область:** таблица:

- имя файла;
- стадия ПД/РД/ИД;
- дисциплина;
- шифр документа;
- редакция;
- статус согласования;
- актуальная редакция или нет;
- статус первичной проверки файла;
- причина выбора/отклонения редакции.

**Действия:** открыть/скачать файл, вернуться к загрузке реестра, если процесс допускает дозагрузку. Скачивание файла — через временный URL. Возможность повторной загрузки зависит от статуса процесса.

**API:** `GET /processes/{id}/files`, `GET /files/{id}/download-url`.

**Важно:** не показывать загрузку как доступную после `FINALIZED` или в запрещенном backend статусе; API отвечает конфликтом 409.

## Страница 8. Проверка: протокол

**Маршрут-пример:** `/checks/{processId}/protocol`

**Задача:** главный экран ручной проверки результатов.

**Шапка:** объект, дата/номер проверки, статус; вкладки проверки; индикатор числа неразобранных кандидатов.

**Верхняя сводка:**

- всего findings;
- требуют решения (`CANDIDATE` и/или `inspector_status=PENDING`);
- подтверждены инспектором;
- отклонены;
- требуют уточнения.

Это агрегаты, которые интерфейс может вычислить из массива `findings[]`; отдельных счетчиков API не дает.

**Панель фильтров:**

- статус результата;
- приоритет HIGH/MEDIUM/LOW;
- раздел/параметр Матрицы;
- только требующие решения.

**Список карточек:**

- код и название параметра;
- приоритет;
- ожидаемое и фактическое значения с единицей;
- дельта;
- короткое объяснение (`rationale`);
- статус системы и решение инспектора;
- кнопка «Открыть доказательства».

Порядок приходит из API: кандидаты первыми, внутри по приоритету. Сохранять его по умолчанию.

**Пустые/особые состояния:**

- нет findings — обработка не нашла результатов либо еще не готова; текст должен учитывать статус процесса;
- все решения приняты — показать завершение верификации;
- мало данных — объяснить `MISSING_EVIDENCE`;
- нельзя сравнить — показать причину, если она есть в rationale.

**API:** `GET /processes/{id}/protocol`, `GET /params`, при открытии подробностей — `GET /findings/{id}`.

## Страница 9. Детали finding и просмотрщик документов

Это может быть широкая отдельная страница или правая выдвижная панель поверх протокола. Для настольного рабочего места предпочтительна панель/двухколоночный просмотр, чтобы пользователь не терял список findings.

**Шапка панели:** код/название параметра, приоритет, статус; кнопка закрытия/возврата к списку.

**Левая колонка:**

- объяснение системы;
- ожидаемое значение и источник;
- фактическое значение и источник;
- delta и единица;
- история решения, если API ее предоставляет (текущая схема содержит автора/дату последнего решения, но не историю версий решений).

**Правая колонка — документы:**

- документы ожидаемой и фактической сторон рядом;
- название файла и стадия;
- страница;
- цитата и извлеченное значение;
- PDF-страница с подсветкой `bbox`, если геометрия известна;
- для DOCX/XML или неизвестной геометрии — показать цитату и страницу/контекст без точной подсветки;
- ссылка на скачивание через краткоживущий URL.

**Блок решения:**

1. «Подтвердить нарушение» — решение `CONFIRMED_VIOLATION`, комментарий обязателен.
2. «Отклонить расхождение» — `NEGATIVE_VERIFIED`, обязательны причина и комментарий. Причины: неверная редакция, согласованное изменение, ошибка OCR, ошибка связывания, неприменимо, дубликат, другое.
3. «Запросить уточнение» — `CLARIFICATION_REQUIRED`; комментарий полезен для понимания, контракт не помечает его обязательным.

Показывать обязательность полей до отправки, ошибки 400 рядом с соответствующим полем, конфликт 409 как сообщение, что статус процесса уже не допускает решение.

**API:** `GET /findings/{id}`, `GET /files/{file_id}/download-url`, `POST /findings/{id}/decision`.

## Страница 10. Финализация и передача

**Маршрут-пример:** секция обзора проверки или отдельная вкладка «Завершение».

**Задача:** показать, что именно будет зафиксировано и куда передан результат.

**До финализации:**

- сводка по результатам;
- список/счетчик нерешенных `CANDIDATE`;
- кнопка «Финализировать проверку» только для `COMPLETED`;
- пояснение, что после действия изменения и дозагрузка запрещены;
- диалог подтверждения с названием объекта и процессом.

**После финализации:**

- статус `FINALIZED` и дата;
- статус синхронизации с ИАИС «РиН»: ожидает, синхронизировано, ошибка;
- дата последнего обновления;
- для `supervisor`/`admin` — «Отменить финализацию», причина обязательна.

**API:** `POST /processes/{id}/finalize`, `GET /processes/{id}/sync`, `POST /processes/{id}/unfinalize`.

**Ограничение:** ручки повторной отправки синхронизации нет. При `SYNC_FAILED` сообщить статус и дать request ID/инструкцию обратиться к ответственному; не рисовать кнопку «Повторить», пока backend ее не добавит.

## Страница 11. Справочник параметров Матрицы (по необходимости)

**Маршрут-пример:** `/parameters`

**Задача:** искать и объяснять параметры, по которым система сравнивает документы.

**Шапка:** заголовок «Параметры Матрицы», версия Матрицы.

**Основная область:** список/таблица из 132 параметров: код, раздел, название, единица, приоритет, тип данных, источники в ПД/РД/ИД, логика сравнения. Поиск и фильтры можно реализовать на клиенте после получения каталога.

**API:** `GET /params`.

**Объем первой версии:** можно не делать самостоятельной страницей, а показывать те же данные в карточке результата и добавить ссылку «О параметре».

## 5. Сквозные компоненты

### Индикатор статуса проверки

Единый цвет и текст для каждого статуса процесса, одинаковые в истории объекта, заголовке проверки и обзоре. Не опираться только на цвет: показывать текст.

### Карточка документа

Имя, стадия, редакция, состояние файла и доступность просмотра. Отклоненные файлы явно отделять от принятых.

### Карточка finding

Код/название, приоритет, пара значений, статус, CTA к доказательствам и решению.

### Просмотр PDF

Открывать страницу из `evidence.page`, накладывать `bbox` в нормализованных координатах, показывать рядом цитату. Временную ссылку не кэшировать дольше `expires_at`.

### Ошибки и состояния ожидания

Единый формат API-ошибки: `error.code`, `error.message`, `error.details`, `request_id`. Пользователю показывать `message`, а `request_id` — в деталях ошибки/копируемой диагностике.

## 6. Роли и видимость действий

OpenAPI перечисляет `inspector`, `supervisor`, `admin`, `ml_engineer`. Явно подтверждено только то, что отмена финализации доступна `supervisor` и `admin`. Остальные точные полномочия в контракте не полностью описаны.

Предлагаемое поведение до уточнения матрицы прав:

- скрывать/блокировать «Отменить финализацию» у инспектора и ML-инженера;
- остальные действия показывать на основании фактических ответов backend и согласованной матрицы ролей;
- при 403 показывать отказ в доступе и не терять введенные данные формы.

## 7. Что не закладывать как готовые страницы/функции

В материалах прямо указано, что API пока не предоставляет:

- экспорт протокола в PDF/XML/DOCX;
- поиск и пагинацию на backend;
- администрирование пользователей и Матрицы;
- отдельный список подозрений;
- разбиение finding;
- WebSocket/SSE-обновления;
- refresh-токены.

Это можно оставить в будущем бэклоге, но нельзя включать в обещанный функционал первой версии без расширения контракта.

## Дополнение после сверки репозитория и уточнений владельца проекта

Это дополнение заменяет соответствующие пункты раздела «Что уточнить у владельца продукта до визуального дизайна» выше.

### Решения владельца продукта

- Терминологию интерфейса сейчас не фиксируем; названия вроде «проверка», «процесс», «протокол» можно будет поменять позднее. Внутри API при этом передавать канонические статусы из контракта без изменений.
- Фронтенд должен быть адаптивным: полноценная работа на компьютере и на телефоне.
- Проверку и выводы делает человек-пользователь. Интерфейс оставляет за пользователем запуск проверки, решения по результатам и финализацию.
- Экспорт, серверный поиск/пагинация, уведомления и отдельные экраны аудита сейчас не нужны.
- При сбое передачи пользователь хочет отправить результат повторно. Техническое ограничение текущего API отмечено ниже.
- Проект фронтенда должен жить отдельной папкой рядом с backend-клоном, а не внутри/вместо backend-проекта. Совместный запуск будет настраиваться отдельным фронтенд-проектом и согласованной конфигурацией запуска.

### Что подтвердил репозиторий

Репозиторий [leanid3/LDT2026](https://github.com/leanid3/LDT2026) описывает продукт как сервис автоматической сверки исполнительной документации ПД/РД/ИД с Матрицей нормативных требований для Мосгосстройнадзора. Backend уже содержит Go API, Python-воркеры, движок правил, очередь и файловое хранилище; в README папка `frontend/` отмечена как еще не созданная. Значит, фронтенд — новый отдельный компонент.

В актуальном OpenAPI репозитория присутствуют операции для шаблонов реестра, которых не было в приложенной копии файлов:

- `GET /documents/registry-template` — пустой шаблон;
- `GET /documents/{process_id}/registry-template` — шаблон, заполненный принятыми файлами текущей проверки.

По умолчанию XLSX с листами «Реестр» и «Инструкция», также поддерживается CSV. Поэтому на шаге реестра обязательно нужны кнопки «Скачать шаблон» и «Скачать шаблон по загруженным файлам». Ошибочный реестр можно поправить и загрузить заново; повторная загрузка безопасна, отдельная страница редактирования таблицы не нужна.

Для состояния полноты процесса актуальная схема добавляет `load_warnings[]` с уровнем `info / warning / error` и готовым текстом для пользователя. Их нужно показывать на обзоре проверки и перед запуском, а не придумывать логику на фронтенде по косвенным полям.

### Важное расхождение по повторной отправке в ИАИС «РиН»

Владелец продукта хочет кнопку повторной отправки при ошибке. Архитектура backend сообщает, что `cmd/rin-sync` автоматически делает повторы с интервалами 1, 5 и 15 минут. Но публичный OpenAPI содержит для синхронизации только `GET /processes/{id}/sync` для чтения статуса; ручки повторной отправки нет. После `SYNC_FAILED` фронтенд сейчас не может инициировать новую отправку контрактным способом.

Чтобы требование «нажать и отправить заново» реально работало, backend-контракт нужно расширить отдельной операцией повторной отправки/повтора синхронизации. До этого в интерфейсе показываем статус и автоматические повторы, без фиктивной кнопки. Это вопрос к интеграции фронтенда с backend, а не к дизайну страниц.

### Уточнение про пользователя и роли

Репозиторий задает роли и права: `inspector` может загружать, просматривать, принимать решения и финализировать; `supervisor` дополнительно отменяет финализацию; `admin` управляет Матрицей, нормативами и пользователями; `ml_engineer` читает данные и работает с экспортом датасета/отчетами. Сейчас пользовательский интерфейс строим для обычного рабочего пользователя-инспектора; отдельные административные экраны не включаем. Служебные полномочия не должны менять основной маршрут инспектора.

OpenAPI-схема объекта не содержит `created_by`/владельца, а `GET /objects` не описывает выдачу только объектов текущего пользователя. Поэтому решение пользователя понимаем как «действия проверки выполняет авторизованный человек», а не как доказанную изоляцию объектов по владельцу. Если требуется, чтобы каждый аккаунт видел только созданные им объекты, это нужно отдельно обеспечить/подтвердить на backend.

### Адаптивное поведение

- **Компьютер:** постоянная боковая навигация; таблицы объектов и документов; протокол слева и просмотрщик доказательств справа; быстрый переход между findings без потери позиции.
- **Телефон:** боковое меню превращается в верхнее меню/выдвижную панель; таблицы становятся карточками с ключевыми полями; фильтры открываются отдельной панелью; форма и загрузка идут в одну колонку.
- **Телефон, просмотр доказательств:** сначала карточка расхождения, затем переключатель «Ожидаемое / Фактическое» для просмотра документов по очереди. Не пытаться уместить две страницы PDF рядом.
- **Телефон, решение:** кнопки решений доступны в фиксированной нижней панели; формы причины/комментария открываются в листе/диалоге и остаются читаемыми при клавиатуре.
- На всех размерах экрана можно выполнить весь маршрут: создать объект, загрузить файлы и реестр, просмотреть доказательства, принять решение и завершить проверку.

### Что остается реально открытым по коду и контракту

1. Ручная повторная отправка синхронизации требует новой API-операции; существующие автоматические ретраи сами по себе не обеспечивают кнопку в интерфейсе.
2. Не определено, должны ли объекты изолироваться по создавшему аккаунту: в контракте нет owner-поля/фильтра.
3. В репозитории desktop и mobile UX не описаны; адаптивное поведение выше — продуктовая спецификация на основе решения владельца.
4. Локальная копия репозитория в доступных сейчас каталогах не обнаружена; сверка выполнена по указанному публичному репозиторию и его актуальным README, `docs/frontend-api.md`, `docs/architecture.md`, `docs/glossary.md`, `docs/lifecycle.md`, `docs/registry.md` и `contracts/openapi.yaml`. Код репозитория не менялся.
